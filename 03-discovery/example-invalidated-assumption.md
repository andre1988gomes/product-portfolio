# Example - Invalidating A Core Assumption Through Discovery

## Evidence Metadata

| Field | Value |
| --- | --- |
| Used in | [Discovery Pivot](../01-case-studies/case-study-discovery-pivot/case-study.md) |
| Decision supported | Stop optimizing configuration depth and reframe the problem around a more meaningful adjacent pain point. |
| Evidence type | Discovery artifact, Qualitative, Proxy |
| Confidence level | High |
| Outcome influenced | Problem reframing, scope change, and stronger expected user relevance. |

## Assumption Tested

Users would perceive charging optimization configuration as a primary source of friction and would adopt additional controls or automation to improve the experience.

## Why This Assumption Mattered

If the assumption was wrong:

- adoption of new configuration features would be low
- additional complexity would not meaningfully improve the experience
- product effort would be spent optimizing the wrong layer of the problem

## Discovery Signals Collected

- qualitative interviews centered on recent charging experiences
- support and operational signals related to failed or unexpected outcomes
- end-to-end journey mapping from plug-in to departure

The focus was on outcomes, not feature preference.

## What We Found

Signals consistently showed that:

- users did not see configuration depth as the primary issue
- minor setup friction existed, but it was tolerated
- unreliable charging outcomes were the dominant pain point
- several users said they would not engage with more controls if the core outcome remained unreliable

## Decision

The original direction was invalidated.

The initiative pivoted from:

- improving configuration and optimization controls

to:

- improving outcome reliability, monitoring, and recovery

## Key Learning

In complex automated systems, users optimize for outcomes more than control. Discovery has to be allowed to invalidate the problem framing itself, not just refine the solution.
